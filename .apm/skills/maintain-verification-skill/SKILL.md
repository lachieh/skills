# Maintain A Verification Skill

A feature map begins drifting when the application changes. This skill maintains
a skill generated by `create-verification-skill`, or any project-local
verification skill with a feature map. The unit of rigor is the feature: cover
every feature file from source and exercise every feature live without turning
every bullet into a separate terminal session.

The boss coordinates the pass and owns decomposition, app driving, worker
review, integration, outcome selection, and final claims. Source readers remain
read-only. Bounded corrections delegate to one implementation owner by default.

## Outcomes

Pick one and report it:

- **clean:** Every feature received source and live coverage. There is no change
  worth shipping, so create no branch or pull request.
- **changed:** One pull request contains proven documentation, harness, or map
  corrections.
- **blocked:** Coverage could not finish or a proven correction could not ship
  safely. State the exact blocker.

## Edit Scope

Edit only the verification skill's directory: its `SKILL.md`, `features/`, and
owned harness scripts. Do not edit product code during the pass. Behavior that
the map describes but the application no longer provides is either
documentation drift or a product regression. Correct the map for drift and
report product regressions without hiding them in documentation.

## Pass

0. **Locate the target.** Find a project-local verification skill with launch
   and drive sections plus a feature map, usually under
   `.agents/skills/verify-*/`. If several candidates exist, ask which one to
   maintain. If none exists, stop and point to `create-verification-skill`.
1. **Check index integrity.** Read the feature-map README and enumerate sibling
   files. Record missing, extra, duplicate, and dead entries for correction
   without generating a separate inventory.
2. **Run the source wave.** Launch one read-only worker per feature file
   concurrently. Resolve the `exploration` role at `S` size through
   `configure-models`. Each worker explains how the user-facing feature works
   from source, cites likely documentation drift, and returns one concise live
   recipe. Workers do not drive the application or edit files. Require this
   shape: feature summary, source entry points, likely drift or none, one recipe.
3. **Reconcile.** Account for every feature file and returned summary. Merge
   overlapping recipes into as few application states as practical. Spot-check
   cited drift rather than re-proving clean claims. Sweep recent changes for
   user-facing behavior missing from the map, and require a concrete source path
   before calling a feature missing.
4. **Run the live pass.** This is required even when source appears clean. The
   boss owns all driving and follows the verification skill's launch strategy:
   one long-lived instance driven serially for servers and UIs, or a fresh
   isolated session per drive for short-lived CLIs. Exercise every feature at
   least once.

   Maintain these invariants throughout the live pass:

   - Run doctor before the first drive, for each fresh session when sessions are
     the unit, and after any failed or surprising drive. If doctor cannot detect
     a stuck UI state, reset to known state or relaunch.
   - Check that captured evidence survives every cleanup at its named location.
   - Remove residue when a drive no longer needs it. For a shared instance,
     remove the residue rather than the instance.

   A doctor failure caused by skill drift is drift. Delegate a bounded correction
   early through the implementation owner from step 6 and retry once, restarting
   only what the correction invalidated. A feature is `verified-unreachable`
   only when the report names the concrete prerequisite and attempted route. If
   the map omits that prerequisite, include it in the correction set. Re-drive
   every harness correction before shipping it. Perform final teardown after the
   final drive and re-proof while retaining evidence.
5. **Triage.** A wrong or missing user-facing description is documentation drift.
   Behavior that works but cannot be driven is a harness gap. Broken application
   behavior is a product gap and stays outside this run's edits. Helpers remain
   executable and documented in the skill body.
6. **Implement accepted corrections.** Resolve the `implementation` role at `M`
   size through `configure-models` and delegate one bounded owner by default.
   Give it only verified documentation, harness, and map corrections. The boss
   reviews every changed file, integrates the result, and independently re-runs
   affected live recipes.
7. **Ship or stop.** For `changed`, create one pull request of proven corrections
   after rereading every changed file. For `clean` or `blocked`, create no pull
   request and report coverage accurately. Apply `principle-prove-it-works`
   before the outcome claim.

Keep concise run notes covering features, unreachable prerequisites, confirmed
drift, and outcome in a scratch location. Do not commit those notes.
